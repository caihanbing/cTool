# cURL compatibility

cTool imports cURL command text as data. It does not invoke Bash, CMD, PowerShell, cURL, a local script, or a local file path. Parsing a command never runs substitutions or shell expressions. The request ultimately uses the browser's Fetch and extension network APIs, so it is not a replacement for system cURL.

## Supported command forms

- Chrome/Edge DevTools Bash commands using single or double quotes, backslash escapes, and `\\` line continuations.
- Windows CMD commands using double-quoted arguments, caret escapes, and `^` line continuations. `curl.exe` is accepted.
- A positional URL or `--url`; one URL per command.
- `-X` / `--request`, `-H` / `--header`, `-b` / `--cookie` with literal cookie values, and `-u` / `--user` Basic authentication.
- `-d`, `--data`, `--data-raw`, `--data-binary`, `--data-ascii`, and `--data-urlencode`.
- `-F` / `--form` and `--form-string` for multipart fields. A `@path` field prompts for a browser-selected file; cTool never reads the path itself.
- `-e` / `--referer`, `-A` / `--user-agent`, `-G` / `--get`, `-I` / `--head`, `-L` / `--location`, and `--max-time`.
- Common browser methods: GET, HEAD, POST, PUT, PATCH, DELETE, and OPTIONS.

Repeated query parameters retain order. An explicit method takes precedence over the method inferred from body options. Empty text bodies and duplicate headers are retained in the request model, subject to browser restrictions.

## Rejected options

cTool reports unsupported options instead of silently changing transport behavior. This includes proxies (`-x`, `--proxy`, `--preproxy`), certificate and key files (`--cacert`, `--cert`, `--key`), network routing (`--resolve`, `--connect-to`, `--interface`, Unix sockets), cookie jars (`-c`, `--cookie-jar`), local config/scripts (`--config`), and delegated authentication modes such as Digest or NTLM. Custom per-part headers and separate connection timeouts are not available.

## Accepted with a browser-behavior notice

- `--compressed`: compression negotiation and decompression are browser-controlled.
- `-k` / `--insecure`: ignored with a notice; browser TLS certificate verification remains enabled.
- `--http1.0`, `--http1.1`, `--http2`, `--http2-prior-knowledge`: the browser chooses the protocol version.
- `--path-as-is`: the browser may normalize URL paths.
- `-i` / `--include`: response headers are shown in the response panel.
- `--fail` / `--fail-with-body`: HTTP error bodies remain visible instead of becoming cURL process exit codes.
- `-v` / `--verbose`: verbose cURL transport logs are unavailable.
- `-o` / `--output`: the filename is ignored; use the response download action.

## Browser transport differences

- Browser profile cookies are never sent automatically. Only explicitly entered cookies can be replayed.
- Manual Cookie, Referer, Origin, and User-Agent values are applied to the exact initial URL and method. They are not forwarded to a different redirect target.
- Redirects are blocked by default. Enabling follow uses browser behavior; when disabled, browsers may report an opaque redirect error. cTool cannot promise the raw 3xx body or a complete redirect chain.
- The browser controls restricted headers, TLS, compression, protocol version, cache, and content decoding. Browser-controlled request headers such as Host and Content-Length are rejected.
- GET and HEAD request bodies are blocked. Multipart boundaries are generated by the browser, so an imported multipart Content-Type boundary is replaced.
- Responses above 20 MiB are stopped. The UI preview is limited to 1 MiB; binary bodies are offered as raw downloads.
- cTool does not support proxy configuration, local cURL configuration files, shell environment expansion, or server-side TLS client certificates.
